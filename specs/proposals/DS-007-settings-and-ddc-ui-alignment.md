## 用户决定

1. Windows 必须提供独立“关于”页面，不再把关于信息藏在“常规”页弹窗中。
2. macOS 显示器页补齐 DDC 参数读取入口、亮度/对比度/音量滑杆和各项托盘显示开关。
3. macOS“联动调节所有显示器”从“常规”移动到“显示器”。
4. macOS 窗口标题必须在标题栏视觉居中。
5. 两端移除设置窗口全局“取消/保存”；设置按安全的即时持久化规则生效。
6. macOS 浅色模式内容区使用明确的系统语义背景色。
7. Windows 为亮度、对比度、音量补齐各项托盘显示开关和托盘调节入口。
8. 产品尚未公开发布，不保留 v1 网络协议或 v3 及更早本机配置兼容路径。
9. 两端显示器页只保留一个全局控制通道选择器、联动调节开关，以及每台显示器的 DDC 功能开关、托盘显示开关、滑杆和只读刷新入口；删除其他可编辑字段。
10. macOS 修复协同状态长期显示“等待 Windows 心跳”或“无响应”的问题；状态必须按所选配置和实际 v2 探测结果展示，不得硬编码平台角色。
11. macOS 修复连续多次 DDC 调节后控制不可用的问题；连续滑杆输入必须合并、串行执行，并能在原生后端失效后安全恢复。
12. Windows 和 macOS 的显示器控制采用紧凑布局；普通界面不显示 VCP 编号、后端术语或重复的“启用/开”文字。
13. Windows 与 macOS 的全部设置页面统一信息架构、字段名称、排列顺序、交互语义、内容密度和状态反馈；保留各平台原生视觉控件，不要求像素级复制。

- “联动所有显示器”已位于显示器页。
- 托盘没有按 DDC 项控制显示/隐藏的配置，也没有等价的托盘滑杆入口。
- 所有页面共用底部“取消/保存”。

### macOS

- 已有独立关于标签和托盘 DDC 滑杆。
- 设置页显示器卡片仍以名称、selector、输入源和 DDC 回读开关为主，没有完整的三项 DDC 滑杆及每项托盘显示开关。
- “联动调节所有显示器”位于常规页。

- 浅色模式内容页没有稳定的系统语义背景填充。
- 所有页面共用底部“取消/保存”。

- 菜单滑杆的每次变化都会排入 DDC 写入队列；当前没有按“显示器 + VCP 项”合并连续写入，也没有覆盖原生 IOAVService 句柄失效后重新发现并重试的长期压力测试。

## 建议行为

### 1. 双端页面结构

两端统一为五个标签，顺序固定为：

1. 常规
2. USB 切换
3. 协同
4. 显示器
5. 关于

Windows 关于页至少展示应用图标、产品名、版本/构建、平台/架构、协议版本、GitHub、许可证和测试构建提示。macOS 保持等价内容。关于页只读取公开应用元数据，不读取本机配置，不触发网络或硬件。

### 1.1 双端设置页面统一规范

“统一”表示同一功能在两端具有相同的页面归属、名称、顺序、默认值、启用条件、保存时机、错误状态和帮助说明。AppKit 与 WinUI 3 继续使用各自原生控件、字体渲染、窗口按钮和无障碍行为，不追求像素级一致。

全局布局规则：

- 五个标签的名称、顺序和图标语义一致；切换标签时窗口标题同步更新。
- 页面使用相同的内容顺序：主要开关 → 核心字段/列表 → 状态与错误 → 简短说明。
- 简单开关不单独占用大卡片或整行说明区；能在同一逻辑行表达的控件保持同一行。
- 标签短而面向用户，不显示协议字段名、VCP 编号、schemaVersion、endpointID、后端类名或平台 API 名称。
- 技术细节只进入诊断或高级信息；普通错误提示说明“发生什么、是否已保存、用户下一步”，不显示敏感值或内部异常堆栈。
- 两端使用相同的空状态、进行中、成功、警告和错误语义；颜色之外必须有文字或图标，不能只靠红绿区分。
- 页面说明控制在一至两行；不重复控件标题，也不长期展示实现限制说明。
- 窗口大小、内容边距、组间距和控件高度在各平台内部一致；长页面使用内容区滚动，不滚动顶部标签。
- 键盘导航顺序与视觉顺序一致；所有开关、按钮、输入框和滑杆提供可访问名称。

各页统一内容如下：

| 标签 | 双端统一内容 | 不再显示 |
| --- | --- | --- |
| 常规 | 登录时启动；必要的应用级常规开关 | 关于按钮、联动 DDC、协议或硬件技术说明 |
| USB 切换 | USB 自动切换、返回本机时按需切屏、当前配置的学习/选择入口和状态 | 原始 VID/PID、设备路径、重复的旧单对端字段 |
| 协同 | 配置选择/增删排序、名称、地址、端口、配对码、启用、检测、每显示器输入源映射和状态 | v1 回退说明、endpointID、协议字段名和“保存后生效”文案 |
| 显示器 | 全局控制通道、联动开关、检测/刷新、每台显示器三项紧凑 DDC 控制 | 可编辑名称/识别码、selector、设备路径、VCP 编号、旧本机/对端输入源 |
| 关于 | 图标、产品名、版本/构建、平台/架构、协议版本、项目和许可证入口、构建性质 | 本机配置、IP、配对码、USB/显示器标识和硬件操作入口 |

双端统一用词：

- `常规`、`USB 切换`、`协同`、`显示器`、`关于`
- `登录时启动`
- `USB 自动切换`
- `回到本机时按需切屏`
- `启用此配置`
- `检测`
- `控制通道`
- `联动调节所有显示器`
- `读取 DDC 参数`
- `亮度`、`对比度`、`音量`
- `在托盘显示`（macOS 界面也使用该统一产品术语；辅助说明可注明“菜单栏”）

不得在同一含义上分别使用“对端/Windows/Mac”“开启/启用”“读取状态/刷新数值”等多套词汇。动态目标一律显示用户自定义配置名称。

### 2. 即时持久化

设置窗口不再显示全局“取消”和“保存”按钮，关闭窗口只关闭界面，不承担提交或回滚语义。

- 开关和单选/下拉选择：用户操作后立即原子保存，保存成功后才更新运行时。
- 滑杆：拖动时可以预览；停止拖动或键盘提交后执行一次受控 DDC 写入，写入成功才更新缓存。滑杆本身不是配置提交按钮。
- 文本字段：在结束编辑或按 Return 后校验并原子保存，不按每个字符保存。
- 添加、排序和删除协同配置：操作完成后立即原子保存；删除仍需确认。
- endpoint 首次发现或变化：用户确认后立即原子保存，不再提示“还需点击保存”。
- 校验或写入失败：保留最后一次有效持久化值、恢复控件并显示就地错误；不得让半完整配置进入运行时。
- 尝试开启不完整协同配置时拒绝开启并指出缺失字段。
- 配置安全状态只能在一次完整、原子且回读一致的 v4 保存成功后解除。

### 3. 显示器页

显示器页顶部只保留两个全局设置：

- `controlChannel`：单一控制通道选择器。macOS 可选“自动/原生 DDC/m1ddc 回退”，Windows 可选“自动/原生 DDC/ControlMyMonitor 回退”；平台只展示实际可用通道。
- `linkAllDisplays`：联动调节所有显示器，默认关闭，切换后立即保存。

每台已检测显示器显示一个不可编辑卡片标题。标题使用系统提供的中性显示名称或序号，不展示或允许编辑原始 UUID、selector、设备路径或其他硬件标识。

每个显示器卡片仅保留：

- “读取 DDC 参数”按钮：只读取亮度、对比度和音量，不写入硬件。
- 亮度：`enabled` 开关、`showInTray` 开关、调节滑杆。
- 对比度：`enabled` 开关、`showInTray` 开关、调节滑杆。
- 音量：`enabled` 开关、`showInTray` 开关、调节滑杆。
- 简短的读取/写入状态和错误提示。

每项 DDC 控制使用一行紧凑布局，建议顺序为：

```text
亮度    [功能开关]  [托盘开关]  [────────滑杆────────]  65
对比度  [功能开关]  [托盘开关]  [────────滑杆────────]  50
音量    [功能开关]  [托盘开关]  [────────滑杆────────]  20
```

- 行首只写“亮度”“对比度”“音量”，不写“启用亮度”或重复显示开关状态文字“开/关”。
- 功能开关和托盘开关用列标题、图标或简短辅助提示区分；不得让每个开关单独占一整行。
- `VCP 0x10`、`VCP 0x12`、`VCP 0x62`、IOAVService、Dxva2 等实现细节不显示在普通设置页。
- 如诊断确需 VCP 编号，只能放入后续诊断页或高级诊断信息，不能作为日常控件标签。
- 窄窗口下允许滑杆换到同一项目的第二行，但功能开关和托盘开关仍保持紧凑，不拆成多个大区块。

规则：

- `enabled = false` 时该项不读取、不写入，滑杆和 `showInTray` 禁用。
- `showInTray = true` 仅控制托盘/菜单栏入口是否出现，不改变 DDC 能力。
- 新检测显示器的三项 `enabled` 和 `showInTray` 默认均为 `false`，避免新安装猜测硬件能力或让托盘意外出现控制项。
- 只有成功回读或已有可信缓存时滑杆才显示确定值；未知值不伪装为 0。
- 三项全部成功返回 0 仍视为不可信遥测；单项 0 保持合法。
- 联动开启时，只联动其他同时启用相同 DDC 项的显示器；单台失败不阻塞其他显示器。
- 显示器检测、稳定 ID 绑定和后端细节保留在内部模型，不再作为普通设置字段显示。
- 输入源映射只存在于“协同”配置中，不在显示器页重复显示。

### 4. 托盘/菜单栏 DDC 控制

- 两端只为 `enabled = true && showInTray = true` 的显示器和 DDC 项创建调节入口。
- macOS 使用现有菜单滑杆组件，按新开关动态增删。
- Windows 使用托盘子菜单或轻量调节浮层提供等价滑杆；不得把“显示在托盘”简化成只显示不可调节文本。
- 配置变化后托盘内容立即刷新，无需重启应用。
- 打开托盘或刷新显示值可以读取 DDC，但不得写入输入源、唤醒显示器或触发协同。

### 5. macOS 窗口视觉规则

- 当前标签标题在标题栏水平视觉居中，页面切换时同步更新。
- 不依赖透明标题栏造成的偏移；使用 AppKit 原生标题区或等价的居中标题附件。
- 内容区在浅色和深色模式均使用动态系统语义背景色，不硬编码白色或固定 RGB。
- 显示器滚动区、普通页面容器和关于页必须覆盖完整内容区域，不能露出透明底。

### 6. macOS 协同状态

- 删除所有基于 v1 或固定 `windows` 角色生成的设置页在线状态。
- 状态以当前选中的协同配置名称和 v2 endpoint 为单位，不以平台名称判断对端。
- 未启用显示“未启用”；字段不完整显示“配置不完整”；从未主动检测且没有合法心跳显示“尚未检测”。
- 用户点击检测后才进入“正在检测”；只有本次 v2 探测超时才显示“无响应”。
- 收到已认证且 endpoint 匹配的 v2 响应后显示“v2 可用”或“已连接”；6 秒在线窗口过期后显示“连接已断开”，不得重新显示“等待 Windows 心跳”。
- 切换所选配置时立即展示该配置自身状态，不沿用上一配置结果。
- 状态展示不得触发唤醒、DDC、USB 或输入源切换。

### 7. macOS 连续 DDC 调节可靠性

- 同一“显示器稳定 ID + VCP code”的滑杆连续变化采用 latest-wins 合并；正在执行的写入完成后最多再提交最新待写值，不逐个回放已经过时的中间值。
- 不允许同一显示器上多个原生 I2C/DDC 操作并发访问同一传输通道；不同显示器是否并发由后端能力决定，默认串行安全执行。
- UI 主线程不得被 DDC 调用阻塞；滑杆应显示“正在应用/已应用/失败”状态。
- 原生写入失败时，使对应缓存的 IOAVService/显示器传输句柄失效，重新发现一次并仅重试一次；不得无限重试。
- 原生重建仍失败时，可以按用户选择的控制通道使用 `m1ddc` 回退；没有回退时明确报错，但下一次用户操作仍允许重新发现，不能永久标记后端不可用。
- 取消、配置变化、显示器断开或安全闸门关闭时，丢弃待写值；迟到结果不得更新缓存或 UI。
- 只有最终实际写入成功的值才能进入可信缓存。
- 自动读取不能与用户写入互相覆盖：某项有写入进行或待提交时，延后该项自动读取；写入完成后再按需刷新。

## 公共数据结构

本机设置升级到 `schemaVersion = 4`。建议的公共语义如下；平台键名可以遵循原生风格，但语义必须一致。

```text
schemaVersion: 4
controlChannel: string
linkAllDisplays: boolean
displays[]:
  id: stable local logical ID
  brightness: { enabled: boolean, showInTray: boolean }
  contrast:   { enabled: boolean, showInTray: boolean }
  volume:     { enabled: boolean, showInTray: boolean }
collaborationProfiles[]:
  existing v2-only profile fields
```

DDC 当前值、最大值、缓存时间和后端句柄属于本机运行时/缓存，不是网络同步数据。原始硬件标识仍不得进入网络、公共测试向量、日志或 Git。

### 默认值

- `controlChannel = "auto"`
- `linkAllDisplays = false`
- 新显示器的六个 DDC 布尔值均为 `false`
- 首次启动仍只有一个关闭的空协同配置
- 缺少任何 v4 必填字段视为配置不完整，保持零硬件和网络副作用

## v2-only 与不兼容升级

本提案获批后：

- `PROTOCOL.md` 改为只定义 `version = 2`；收到 v1 或其他版本时安全拒绝，不回复、不刷新在线状态、不触发副作用。
- 两端删除 v1 解析器、状态机、发送路径、v1 探测回退和 v1-only UI 文案。
- 能力检测只发送 v2 `status_probe`，结果简化为“v2 可用 / 认证失败 / 无响应 / 本机配置不完整”。
- `contracts/protocol-v1/` 停止作为验收来源，并在独立协调提交中移除。
- v2 消息字段、HMAC、时序、重放保护和 `contracts/protocol-v2/` 均不改变，因此网络消息版本仍为 `2`，不升级为 `3`。
- v3 或更早本机配置不做字段迁移。首次读取时原文件保留为本机备份，应用创建新的 v4 默认配置并保持所有协同和 DDC 写入关闭；不得静默删除旧文件或猜测映射。
- 回滚到旧程序时可以人工恢复旧配置备份；新程序不承诺读取旧配置。

## 安全、验证与回滚

- 自动测试不得执行真实 DDC 写入、输入源切换、USB 交接、唤醒或系统设置修改。
- DDC 回读属于只读操作，但平台自动测试仍使用模拟后端；真实回读单独列入实机验证。
- 配置写入继续使用临时文件、回读校验和原子替换。
- 单端回滚只回退对应平台 PR；共享规范和 v1 contract 的移除必须在两端均通过后再合并。
- 回滚不得删除保存的旧配置备份或覆盖用户当前 v4 数据。
