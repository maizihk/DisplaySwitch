# DS-001：协议 v1 交接状态机一致性提案

## 状态

- 状态：APPROVED（2026-08-27）
- 功能编号：DS-001
- 任务类型：cross-platform
- 基线：`0fed95d4df54536889e1ec6b5a2c54db254c64c5`
- 协议版本：保持 `version = 1`
- 数据版本：公共 contracts 使用 `schemaVersion = 1`；不引入跨端配置同步
- 关联协调记录：`coordination/DS-001.md`
- 公共合同：`contracts/protocol-v1/`，`schemaVersion = 1`

用户已批准本提案列出的五项决定，并授权协调 Agent 创建 `contracts/protocol-v1/`。该批准不授权修改 `PROTOCOL.md` 或任一平台实现；平台实施仍须等待 contracts 完成评审并进入共享基线。

## 背景

当前 `PROTOCOL.md` 已定义六种 UDP v1 消息、十秒有效期、150 ms 防抖和重发、600 ms 兜底、六秒在线窗口以及离线降级。macOS 与 Windows 已实现主要流程，但两端的消息校验、重复消息处理、未知类型处理和自动测试覆盖并不完全一致。

macOS 已有独立的消息校验和重放判断测试，但交接时序仍与 App/UI/硬件动作耦合。Windows 交接逻辑集中在 `Controller`，尚无可在无硬件环境运行的状态机测试。缺少共同测试向量会使两端在不改变 JSON 字段的情况下逐渐产生行为差异。

## 目标

1. 把现有协议 v1 的有效输入、拒绝路径、时序和副作用边界写成双端一致的可测试行为。
2. 为两端分别抽取纯状态机提供共同输入/输出模型，不规定 Swift 或 C++ 内部架构。
3. 建立脱敏公共测试向量，确保两端对正常、重复、过期、乱序和错误输入作出一致决定。
4. 保持现有用户可见交接顺序、超时和离线降级行为。

## 不处理的范围

- 不新增或删除网络消息类型、字段或端口。
- 不修改 `pairingCode` 的安全模型，不引入 HMAC、加密、nonce 或自动发现。
- 不同步显示器、USB、IP、路径、配对码或其他本机配置。
- 不实施 Windows 动态多显示器模型或 macOS DDC 后端重构。
- 不修改防火墙、系统网络、登录项或签名设置。
- 不要求真实 DDC、真实 USB 交接或显示器睡眠/唤醒测试。

## 当前行为

两端目前都能发送和接收 `handover_request`、`usb_present`、`usb_attached_and_awake`、`committed`、`status_probe` 和 `status_response`，并实现主要超时流程。

已确认的差异包括：

- macOS 明确校验 UUID、有限时间戳和本地配对码最小长度；Windows 接收路径没有全部等价校验。
- macOS 以 `type + eventID` 识别重复消息；Windows 只使用最新请求时间戳过滤更旧请求。
- macOS 未知消息类型无法解码；Windows 当前可能先把未知但其他字段匹配的消息计入在线状态。
- 重复 `handover_request` 在 Windows 可能重复执行唤醒；macOS 对同一当前事件只唤醒一次，但可再次发送确认。
- Windows 收到不匹配当前事件的 `committed` 时仍更新用户状态；macOS 只清理匹配事件。

## 建议行为

### 1. 消息结构与字段校验

接收端必须先完成全部校验，再刷新在线状态或把消息交给状态机：

| 字段 | 类型 | 必填 | 合法范围与行为 |
| --- | --- | --- | --- |
| `version` | JSON number，整数 | 是 | 必须为 `1`；其他版本安全拒绝 |
| `type` | JSON string | 是 | 必须是 v1 六种已知类型之一 |
| `eventID` | JSON string | 是 | 必须可解析为 UUID；比较时不区分 UUID 字母大小写 |
| `source` | JSON string | 是 | 必须是对端平台，且与当前接收端方向匹配 |
| `target` | JSON string | 是 | 必须是当前平台 |
| `timestamp` | JSON number | 是 | 有限 Unix 秒；与接收端当前时间绝对差不超过 10 秒，边界包含 10 秒 |
| `pairingCode` | JSON string | 是 | 必须与本机已配置值精确相等；本机配置必须满足现有至少 8 位要求 |
| `wakeSucceeded` | JSON boolean | 否 | 缺少时按“未报告”处理；不得把缺少解释为成功或失败 |

补充规则：

- 缺少必填字段或字段类型错误时拒绝整条消息。
- 未知顶层字段忽略，以保留 v1 内的向前兼容能力。
- 未知消息类型、未知版本、解析失败或校验失败时不回复、不刷新在线状态，也不产生硬件或 UI 状态副作用。
- 本提案不改变配对码编码或长度计算语义。公共向量仅使用 ASCII 示例值，避免把平台字符串计数差异引入 v1。

### 2. 在线状态

- 任一通过完整校验的已知 v1 消息都可以证明对端当前可达，并刷新最近合法消息时间。
- “在线”窗口为最近合法消息后 6 秒，包含边界时刻。
- Windows 每 2 秒发送 `status_probe`；Mac 对每个合法 probe 使用相同 `eventID` 回复 `status_response`。
- 状态消息不得调用 USB、显示器唤醒或 DDC 接口，也不得启动交接状态迁移。
- 重复合法 `status_probe` 可以再次回复，但每次仍必须保持零硬件副作用。

### 3. 出站交接

当本机 USB 从存在变为消失时：

1. 等待 150 ms，并再次确认 USB 仍不存在。
2. 如果 USB 已返回，取消本次候选交接，不发送请求、不切屏。
3. 创建新的 UUID 作为当前出站事件。
4. 若最近 6 秒内没有合法对端消息，发送一次 `handover_request` 后立即执行本机 DDC 切屏。
5. 若对端在线，在相对时间 0、150、300、450 ms 最多发送 4 次同一事件的 `handover_request`。
6. 收到可完成当前事件的确认时立即切屏；否则在 600 ms 时兜底切屏。
7. 切屏完成后发送同一 `eventID` 的 `committed`；`wakeSucceeded` 表示本次切屏调用结果。
8. USB 在等待期间返回时取消当前出站事件；已排队的重发和兜底不得再产生动作。
9. 每个出站事件最多执行一次 DDC 切屏和一次逻辑提交。

### 4. 入站交接与幂等性

- 首次接受新的 `handover_request` 时，把它设为当前入站事件并请求一次显示器唤醒。
- 同一 `type + eventID` 在十秒保留窗口内视为重复。
- 当前入站事件的重复 `handover_request` 不得再次唤醒显示器；如果 USB 已在本机，可以重新发送 `usb_attached_and_awake`，用于弥补确认丢包。
- 时间戳早于最近已接受入站请求的新事件视为乱序并拒绝；时间戳相等时维持现有兼容行为，允许新 UUID 成为较新事件。
- `usb_attached_and_awake` 只有在 `eventID` 等于当前出站事件时才能完成交接。
- `committed` 只有在 `eventID` 等于当前入站事件时才能清理该事件或更新相应完成状态。
- 重复或迟到的确认、提交不得触发第二次切屏，也不得清理其他事件。

### 5. `usb_present` 的事件关联

USB 可能先于 `handover_request` 到达目标端，因此目标端发送 `usb_present` 时可能不知道源端随后创建或正在等待的事件 ID。为保留现有流程：

- `usb_present.eventID` 必须是合法 UUID，但不要求等于源端当前出站事件 ID。
- 源端仅在自己恰有一个当前待处理出站事件时，才可用首次接受的 `usb_present` 完成该事件。
- 没有待处理出站事件时，`usb_present` 只更新物理状态，不触发 DDC。
- 同一 `usb_present` 的重复包不得产生重复切屏。

### 6. 重复记录与清理

- 状态机至少在消息十秒有效期内保留足以识别重复消息的记录。
- 实现可以采用有界缓存，但不得因无界增长造成资源耗尽。
- 重新配置、关闭协同或停止网络接收时，应清理未完成事件和重复记录；不得在重新启用后执行旧事件。

## 状态机公共观察结果

公共测试不比较平台 UI 文案或线程实现，只比较可观察结果：

- `send(type, eventID, wakeSucceeded?)`
- `schedule(timerName, delay)` / `cancel(timerName)`
- `requestWake(eventID)`
- `requestSwitch(eventID)`
- `setPeerReachable(Boolean)`
- `setIncomingEvent(eventID?)`
- `setOutgoingEvent(eventID?)`
- `ignore(reason)`

平台可以使用不同内部类型，但必须能在测试中映射到这些逻辑结果。

## 兼容策略

### 向后兼容

- 保持 `version = 1`、六种消息名称、全部字段名称和 JSON 编码不变。
- 正常 v1 对端不需要协商或迁移即可继续通信。
- 150 ms、4 次、600 ms、6 秒和 10 秒常量不变。

### 向前兼容

- v1 接收端忽略未知顶层字段。
- 未知消息类型和未知 `version` 安全拒绝，不猜测其语义。
- 本提案不提供 v2 降级或协商机制；该问题留给未来 HMAC 提案。

### 行为收紧影响

Windows 对非法 UUID、未知类型和重复请求的处理会变得更严格。这些输入不属于当前协议定义的合法 v1 消息，因此计划作为实现偏离修复，不提升协议版本。若评审认为现有外部客户端依赖这些宽松行为，则必须停止平台实施并重新评估版本变化。

## 迁移与失败安全

- 不改变本地配置格式，无数据迁移。
- 不改变平台本机配置的 `schemaVersion`；公共 contracts 独立使用 `schemaVersion = 1`。
- 状态机重构必须继续读取现有配置；配置无效时保持自动操作停用。
- 解析、验证、状态恢复或依赖注入失败时，不执行唤醒、USB、DDC 或旧事件补偿动作。
- 不删除或覆盖用户现有配置。

## 平台实施边界

### Windows

- 从 `Controller` 提取纯状态机；WinUI、Winsock、USB watcher、唤醒和 DDC 保持适配器角色。
- 增加可在无网络、无硬件环境运行的自动测试目标。
- 补齐 UUID、消息类型、重复和副作用校验。
- 只修改 `Windows/` 和 `handoffs/windows.md`。

### macOS

- 从 App delegate/UI 和硬件调用中提取纯状态机；Network.framework、USB monitor、唤醒和 DDC 保持适配器角色。
- 将现有消息校验和 replay guard 测试扩展为虚拟时间状态机测试。
- 只修改 `macOS/` 和 `handoffs/macos.md`。

任一平台不得修改共享 proposal、contract、`PROTOCOL.md` 或另一平台目录。

## 实施顺序

1. 已完成：评审并批准本提案中的行为定义。
2. 已完成：协调 Agent 创建公共 schema/测试向量并提交评审。
3. 两个平台从同一已批准协调基线创建独立分支。
4. 两端分别实现并运行公共向量与平台测试。
5. 协调 Agent 核对提交、handoff、构建和 CI 后进行跨平台验收。
6. 只有两端均通过时，DS-001 才能标记为 `READY_TO_MERGE`。

Windows W-002 可以独立进行，但不得与 DS-001 共用平台分支或顺手修改状态机。

## 验收条件

- Windows x64 Release 构建和全部自动测试通过。
- macOS Debug、Release、相关 XCTest、构建脚本和严格签名验证通过。
- 两端通过相同公共测试向量。
- 网络 `version` 均为 1，公共 contracts 的 `schemaVersion` 均为 1，且未引入配置同步。
- 非法、旧版、重复和乱序输入的处理一致。
- `status_probe/status_response` 使用相同 `eventID` 且无硬件副作用。
- 两端 handoff 的分支、提交、测试和 CI 记录与远端一致。
- Git 中没有秘密、个人硬件标识、个人路径、真实 IP、配对码或构建产物。
- 自动测试与任何后续实机验证明确区分。

## 回滚方案

- 提案或公共向量不获批准时，不启动平台修改；删除或关闭协调分支即可，运行时不受影响。
- 单个平台实现失败时回退该平台 PR，另一端不得依赖未合并的新内部状态机。
- 若公共向量暴露必须改变已发布字段语义的需求，停止 DS-001 实施，另起需要版本评审的协议提案。
- 回滚后继续使用当前 `PROTOCOL.md` v1 和现有平台实现。

## 已批准的决定

用户于 2026-08-27 批准以下五项决定：

1. 在不提升 `version` 的前提下，将非法 UUID、未知消息类型和重复副作用视为实现偏离并收紧。
2. 同一当前请求的重复包不得重复唤醒，但允许重发确认。
3. `usb_present` 可完成当前唯一待处理出站事件，不要求其事件 ID 相同。
4. 任一完整合法的已知 v1 消息都可刷新六秒在线窗口；非法或未知消息不得刷新。
5. 提案获批后允许协调 Agent 创建 `contracts/` 下的脱敏公共 schema 和测试向量。
